## 3. 必须优先处理

### P1-1：账号保存缺少按账号去重

**证据**

`saveAccount()` 先通过 `sanitizeAccount()` 为没有 ID 的输入生成随机 ID，随后只按 ID 查找已有账号。现代门户和原页面捕获保存账号时通常不提供 ID，因此同一个“学号 + 后缀”每次登录都可能新增一条记录。

**影响**

- 账号列表不断出现重复项；
- `selectedAccountId` 被最新重复项替换；
- 网络参数更新只命中其中一项；
- 保活和下线可能使用旧副本。

**建议**

当输入没有明确 ID 时，用规范化后的 `username + suffix` 作为自然键进行 upsert；存在重复历史数据时保留最近更新时间、非空网络参数和用户自定义名称，并一次性合并。

**建议测试**

- 连续两次从门户保存相同账号，账号总数保持 1；
- 同学号不同运营商后缀保留为不同账号；
- 第二次捕获的新网络参数更新原账号而不是新增；
- 显式 ID 编辑仍只更新指定账号。

### P1-2：临时账号登录后的下线目标可能错误

**证据**

弹窗和现代门户在“不要保存账号”时把临时账号传给 `drcom:login`，但后续 `drcom:logout` 没有传账号。后台下线会回退到 `selectedAccountId`，它可能是另一个已保存账号。

**影响**

用户用临时账号登录后，下线请求可能使用旧账号的用户名、后缀和 MAC，导致下线失败或操作错误连接。

**建议**

登录成功后把“最近认证身份”写入 `storage.session`。只保存下线所需的账号、后缀和网络参数，不保存临时密码。下线默认使用最近认证身份；用户明确指定账号时再覆盖。

**建议测试**

- 已选账号 A 存在，临时账号 B 登录成功后，下线请求使用 B；
- 后台重启后同一浏览器 Session 仍能使用 B 下线；
- Session 结束后不保留 B 的密码。

### P1-3：成功下线没有同步后台连接状态

**证据**

登录结果会调用 `recordLoginOutcome()` 更新 `storage.session.connection`，但 `logout()` 成功后只返回 DrCOM 结果，没有把连接状态改为离线，也没有清理重试状态。

**影响**

弹窗当次操作能显示离线，但重新打开设置页时 `connection:get` 仍可能返回旧的 `online`，徽标和自动化状态也可能短暂失真。

**建议**

下线成功后清除一次性重试 Alarm，并把连接状态原子更新为 `offline`、`attempt=0`、`nextRetryAt=0`、`blocked=false`。下线失败则保留原在线状态并记录错误。

**建议测试**

- 下线成功后 `connection:get.phase === "offline"`；
- 下线失败保持 `online`；
- 成功下线清除待执行重试。

### P1-4：门户会把本地背景图片暴露在页面 DOM 样式中

**证据**

`portal:config:get` 的公开外观包含完整 `backgroundImage`。内容脚本随后把它写入 `#drcom-modern-root` 的 CSS 自定义属性。虽然内容脚本 JavaScript 运行在隔离世界，但创建的 DOM 和内联样式可被门户页面脚本观察。

**影响**

用户选择的私人照片可能被不受信任或被入侵的门户页脚本读取。当前校验还允许远程 HTTP/HTTPS 背景 URL，可能产生额外网络请求和隐私泄漏。

**建议**

- 默认不要把自定义本地背景同步到第三方/校园门户页；门户只使用主题和强调色；
- 若产品必须同步背景，使用明确的单独开关和风险提示；
- 外观校验只接受本地生成的数据或扩展资源，拒绝任意远程 URL；
- 为 `portal:config:get` 增加测试，确认返回值不含图片数据。

### P1-5：清理旧版明文密码键

**证据**

`getState()` 会读取旧版顶层 `username`、`password` 并迁移到 `drcomAssistantState`，但迁移成功后没有删除旧键。

**影响**

密码会在本地存储中保留两份，扩大泄漏面，也让“删除账号”不等于彻底移除旧凭据。

**建议**

成功写入新状态后调用 `chrome.storage.local.remove(["username", "password"])`。迁移测试应验证“先成功写入，后删除旧键”，写入失败时不得删除。

## 4. 应尽快改进

### P2-1：拆分 1500 行后台脚本

`background.js` 同时承担生命周期、消息路由、状态仓库、账号服务、DrCOM 协议、结果解析、连接状态机、动态脚本、跳转保护和脱敏工具，修改任何一块都需要加载整份文件。

建议按职责拆分为：

- `background/state-store.js`：状态、迁移、串行写入和预算；
- `background/account-service.js`：账号 upsert、选择、删除和网络合并；
- `background/drcom-client.js`：请求构造、解析、错误分类；
- `background/connection-service.js`：登录单通道、重试、状态与保活；
- `background/portal-service.js`：动态内容脚本和跳转保护；
- `background/message-router.js`：权限边界和动作分发；
- `background.js`：只注册 Chrome 生命周期事件。

Manifest V3 Service Worker 可采用 ES Modules，但需要在清单中显式设置 `background.type = "module"`；也可以先用 `importScripts` 做低风险迁移。

### P2-2：合并四份账号解析逻辑

账号解码、后缀归一化、标签生成在 `background.js`、`popup.js`、`options.js` 和 `portal-ui.js` 中重复。当前实现相近，但后续增加运营商或修复编码问题时容易只改一处。

建议建立浏览器/CommonJS 均可加载的 `account-utils.js`，清单、弹窗、设置页和测试统一引用。迁移时先建立表驱动测试，再逐页替换。

### P2-3：给网页消息增加当前门户来源校验

后台目前把所有 HTTP/HTTPS sender 视为网页内容脚本，再依靠动作白名单限制能力，但没有核对 `sender.url` 是否等于当前配置门户。配置切换后，旧标签页中已经注入的内容脚本仍可能继续发送白名单请求。

建议在处理网页消息前比较 sender 的协议、主机和当前 `portalUrl`，并限制到允许的 frame。对旧自定义网关、错误主机和子框架分别增加拒绝测试。

### P2-4：提高 DrCOM 响应判定的结构化程度

当前登录和在线判断大量依赖返回文本、HTML 和正则表达式。这对网关版本差异有兼容优势，但也会把页面脚本、隐藏文案或异常 HTTP 响应中的关键词当成真实状态。

建议记录一组匿名化真实响应样本，优先按状态码和明确字段判定，正则只作为回退；“在线”“需要登录”“不明确”“不可达”四类应独立表达。非 2xx 响应除明确“已在线”协议码外不应直接判成功。

### P2-5：修复真实浏览器测试的清理竞态

布局测试在 `finally` 中先执行 `child.kill()`，再注册 `child.once("exit")`。子进程若在两步之间退出，Promise 将永远等待；Windows 上还可能残留浏览器子进程。清理前的多浏览器并行测试曾观察到门户预览偶发失败和测试挂起；当前单套稳定版全量测试已通过，但竞态代码仍然存在。

建议：

- 在 kill 前先创建 `once(child, "exit")` Promise，或先检查 `exitCode`；
- 为退出等待增加硬超时和进程树清理；
- 把真实浏览器测试设为顺序执行，逻辑测试仍可并行；
- 每个测试保留独立 profile 和调试端口；
- 把“源码目录不存在”在启动浏览器前直接报告为跳过或配置错误。

### P2-6：建立可重复发布流程

当前源码是 2.5.3，审阅时发现的发布包仍是 2.4.0，README 依赖人工约定。建议增加 `scripts/package-extension.mjs`：

- 从清单读取版本；
- 使用白名单复制发布文件；
- 校验压缩包根目录；
- 禁止包含测试、截图、参考仓库和真实抓包数据；
- 输出 `<name>-<version>.zip` 和 SHA-256；
- 在临时目录解压后运行清单文件存在性检查。

### P2-7：明确凭据威胁模型与 HTTP 风险

项目已经在 UI 中说明数据保存在当前设备，但开发文档还应明确：密码为浏览器本地明文；默认 HTTP DrCOM 登录会把密码放入 URL；扩展无法防御已控制操作系统账号、浏览器配置文件或校园网链路的攻击者。

建议提供“永不保存密码”模式、迁移/删除说明和首次启用自动登录时的简短确认。不要声称本地存储等同于加密存储。

### P2-8：补充破坏性操作确认

稳定版设置页删除账号、恢复默认配置会直接执行。建议至少对“删除包含密码的账号”和“清除自定义背景/自动化配置”给出确认，并明确恢复默认不会删除哪些数据。确认应可键盘操作，测试取消与确认两条路径。

### P2-9：处理未使用或仅兼容用的状态字段

`ui.subtitle`、`ui.density` 当前没有实际渲染消费者；`ui.hideOriginalPortal` 被强制为 true，主要承担旧版本兼容；账号 `note` 没有编辑界面。这些字段不应直接删除，因为可能存在历史状态，但应标记废弃、给出迁移版本，并在下一次 schema 升级后移除或真正实现。

### P2-10：补齐许可证、贡献和 CI

当前根目录没有稳定版许可证、贡献说明和 Git 元数据。

建议：

- 明确稳定版许可证和第三方参考的边界；
- 建立 Git 仓库、`.gitignore`、变更记录和 CI；
- CI 至少运行稳定版语法、逻辑测试、清单合约和单线程浏览器布局测试。

## 6. 建议实施顺序

1. **修数据正确性**：账号自然键 upsert、临时登录身份、下线状态同步、旧凭据键清理。
2. **收紧隐私边界**：门户不接收本地背景图、拒绝远程背景、校验 sender 来源、补充明文/HTTP 提示。
3. **加固测试基线**：修复浏览器子进程清理竞态，保持 `npm run verify` 全绿。
4. **降低维护成本**：抽取账号工具，拆分后台脚本，废弃无消费者状态字段。
5. **自动化发布**：打包白名单、版本校验、SHA-256、干净解压验证、CI 和变更记录。

每个阶段完成后都应保持当前 81 项测试通过，并为本阶段修复的问题补充新测试后再发布。
